## 1. 目的

「刈りどきナビ」は、田んぼを地図上の区画として管理し、品種、出穂日、気象データから出穂後の日平均気温を自動積算して、刈取適期を色分け表示するアプリである。

MVPの価値は次の一文で定義する。

> 出穂日を登録したら、あとは自動積算され、地図を見れば次に刈る田んぼが3秒で分かる。

本アプリの数値は営農判断を補助する目安として扱い、収穫を自動決定するものにはしない。画面上では、適用ルール、気象地点、データ更新日、欠測の有無を確認できるようにする。

## 2. MVPの範囲

### 2.1 実装する機能

1. ユーザー認証と所有圃場の分離
2. MapLibre GL JSと国土地理院タイルによる地図表示
3. 農林水産省筆ポリゴンの選択、または手描きによる圃場登録
4. 圃場名、品種、出穂日の登録
5. 品種×地域の刈取適期ルール適用
6. 圃場に対応する気象観測地点の自動選択と手動変更
7. 日平均気温の履歴取得と日次更新
8. 出穂後積算気温、残り温度、状態の計算
9. ホーム地図、田んぼ詳細、田んぼ登録、田んぼ一覧
10. 収穫日と収穫時積算気温の保存
11. PWAインストール、最終取得データのオフライン閲覧
12. データ欠測、更新遅延、取得失敗の表示

### 2.2 初期スコープ外

- AIによる助言
- 収量・品質予測
- 病害虫予測
- 衛星画像、NDVI
- 水管理、農薬、肥料、作業員管理
- 天気予報を使った到達日予測
- 自動通知
- 複数農場間の高度な権限管理
- iOS/Androidネイティブアプリ

「あと約何日」は、直近の実測気温を使った参考値に限定し、天気予報とは明確に区別する。

## 4. UX・画面仕様

### 4.1 ホーム地図

ホーム地図を起動後の既定画面とする。

- 年度セレクターを上部に配置する。
- 「適期」「接近」「未設定」の件数チップを表示し、タップで絞り込む。
- 圃場ポリゴンを成熟状態で塗り、色だけでなく「適期」「あと126℃」などの文字を併記する。
- 圃場タップで下部シートを開き、積算値、残り温度、状態、気象地点、反映済み日を表示する。
- 下部シートの「詳しく見る」から田んぼ詳細へ遷移する。
- オフラインでは最後に取得した内容を表示し、データ日時を明示する。
- 小面積の圃場ラベルは拡大時のみ表示する。

描画優先順位は次のとおりとする。

```text
適期超過 > 刈取適期 > 刈取接近 > 登熟後半
> 刈りどき前 > 未設定 > 収穫済
```

### 4.2 田んぼ詳細

表示順は以下とする。

1. 圃場名、品種
2. 現在の積算気温と成熟状態
3. 適期開始・中心・終了温度
4. 適期開始までの残り温度
5. 直近実測値による参考残り日数
6. 出穂日、積算開始日、観測地点、反映済み日、データ品質
7. 日別積算グラフ
8. 作付け編集、観測地点変更、収穫登録

参考残り日数は、直近7日中5日以上の有効値がある場合だけ表示する。

### 4.3 田んぼ登録

登録は3ステップとする。

1. **区画選択**: 筆ポリゴンをタップ。該当しない場合は手描きする。
2. **作付け入力**: 圃場名、品種、出穂日を入力する。出穂日は未設定でも登録できる。
3. **確認**: 面積、品種、適用ルール、気象地点を確認して保存する。

保存は一つのトランザクションで行い、初回積算は非同期ジョブにする。保存直後はホームへ戻り、「計算中」と表示する。フォーム内容は端末内へ一時保存し、戻る操作や画面再読込で失われないようにする。

### 4.4 画面遷移

```text
ホーム地図
├─ 圃場タップ → 下部シート → 田んぼ詳細
│                              ├─ 作付け編集
│                              ├─ 観測地点変更
│                              └─ 収穫登録
├─ ＋田んぼ → 区画選択 → 作付け入力 → 確認 → ホーム地図
└─ 一覧 → 田んぼ詳細
```

## 6. データモデル

### 6.1 基本原則

- EPSG:4326で保存し、面積計算時は`geography`または適切な投影を使う。
- 外部筆ポリゴンの形状は候補データとして扱い、登録時に`fields`へコピーする。
- 日別気象観測値を正とし、積算値は再生成可能な表示キャッシュにする。
- 品種ルールと気象地点は作付け単位で確定する。
- 成熟状態とデータ品質を別項目にする。
- ルール改定で過去表示が勝手に変わらないよう、適用値を作付けへスナップショット保存する。

### 6.2 テーブル

| テーブル | 役割 | 主な列 |
|---|---|---|
| `accounts` | データ所有者 | `id`, `display_name` |
| `fields` | 土地としての田んぼ | `account_id`, `name`, `geom`, `area_m2`, `parcel_source` |
| `crop_seasons` | 年ごとの作付け | `field_id`, `year`, `variety_id`, `heading_date`, `harvest_date` |
| `rice_varieties` | 品種マスター | `name`, `name_kana`, `is_active` |
| `rule_regions` | ルール適用地域 | `kind`, `code`, `name`, `geom` |
| `variety_rules` | 品種×地域の基準 | 適期温度、積算開始規則、根拠、版 |
| `season_rule_snapshots` | 実際に適用した値 | `crop_season_id`, 温度範囲、開始規則、出典 |
| `weather_locations` | 観測所・メッシュ | `provider`, `external_id`, `name`, `location` |
| `season_weather_bindings` | 作付けと気象地点 | `crop_season_id`, `weather_location_id`, `distance_m` |
| `daily_weather` | 地点別の日別値 | `observed_date`, `mean_temp_c`, `quality_code` |
| `weather_import_runs` | 取得監査 | 期間、成否、取得日時、エラー |
| `crop_season_summaries` | 表示キャッシュ | 積算、状態、欠測数、反映済み日 |
| `maff_parcels` | 筆ポリゴン候補 | 外部ID、年度、自治体コード、形状 |

主要制約とインデックスは以下とする。

```text
UNIQUE crop_seasons(field_id, year)
UNIQUE daily_weather(weather_location_id, observed_date)
GIST fields(geom)
GIST maff_parcels(geom)
INDEX daily_weather(weather_location_id, observed_date)
INDEX crop_season_summaries(maturity_status, calculated_at)
```

## 7. VarietyRule

`variety_rules`は次の値を持つ。

```text
variety_id
region_id
harvest_start_temp_c
harvest_target_temp_c
harvest_end_temp_c
danger_temp_c                 # 任意
accumulation_start_offset_days
daily_temperature_metric      # MVPはMEAN
effective_from / effective_to
priority
version
source_title
source_publisher
source_url
published_on
status                        # DRAFT / ACTIVE / RETIRED
notes
```

地域は「全国 → 都道府県 → 市町村・農業地域 → 独自ポリゴン」の階層を許容する。ルール解決の優先順位は以下とする。

1. 作付けに設定したユーザー独自値
2. 圃場を含む最も狭い地域の有効ルール
3. 都道府県ルール
4. 全国ルール
5. 該当なしの場合はユーザー入力を求める

同順位では`priority`、適用開始日、バージョンの順に決定する。根拠が確認できない全国共通値を推測で登録しない。初期データは対象地域の公的な栽培指針等で確認できた品種に限定する。

積算開始はルールごとに保持する。MVPの標準値は出穂翌日の`offset_days = 1`とし、公的指針が出穂当日を含む場合は`0`にする。

## 8. 気象データ設計

### 8.1 Provider境界

気象データ源は以下のインターフェースの背後に置く。

```typescript
interface WeatherProvider {
  findNearestLocations(point: GeoPoint): Promise<WeatherLocation[]>;
  fetchDaily(
    location: WeatherLocation,
    from: LocalDate,
    to: LocalDate,
  ): Promise<DailyWeatherValue[]>;
}
```

MVPでは`JmaAmedasProvider`を実装し、将来`WagriMeshProvider`を追加する。Provider固有の地点ID、認証、レスポンス形式をドメイン層へ漏らさない。

### 8.2 JMA取得方針

- 田んぼ単位ではなく、利用中の観測地点単位で取得する。
- 外部から取得した値はDBへキャッシュし、画面表示のたびに取得しない。
- 気象庁サイトへの過度な自動アクセスを避け、取得間隔、同時実行数、再試行回数を制限する。
- 公式に安定提供が約束されていない内部URLや画面構造への依存を局所化する。
- 取得方法、利用条件、更新時刻、品質フラグを技術検証で確認してから本実装を確定する。
- 将来、より安定した契約データ源へ切り替えられるようにする。

### 8.3 日次処理

```text
06:30 JST
  使用中の地点を重複排除
    ↓
  未取得期間と直近7日を取得
    ↓
  daily_weatherへ正規化・UPSERT
    ↓
  影響を受ける作付けを再計算
    ↓
  crop_season_summaries更新
    ↓
  失敗地点を再試行

12:30 JST
  朝の未取得・失敗分のみ再試行
```

さらに週1回、直近60日を再取得して公表後の訂正を反映する。地点単位の排他ロックを使い、二重取得を防ぐ。36時間以上更新できない場合は運用アラートを発生させる。

出穂日を後から入力した場合は、出穂日から前日までのバックフィルを即時ジョブとして投入する。

## 9. 積算・状態判定

### 9.1 積算

```text
積算気温 = 積算開始日から反映済み日までの有効な日平均気温の総和
```

DBでは小数を保持し、表示時だけ小数第1位へ丸める。欠測値を0℃として扱わず、欠測日数を別途記録する。

### 9.2 成熟状態

```text
HARVESTED       収穫済み
NOT_CONFIGURED  出穂日・ルール・気象地点が不足
BEFORE_HEADING  積算開始日前
GROWING         適期開始の70%未満
GROWING_LATE    70%以上90%未満
HARVEST_SOON    90%以上、適期開始未満
HARVEST_READY   適期開始以上、適期終了以下
OVERDUE         適期終了超過
```

`harvest_date`がある場合は他の条件より優先して`HARVESTED`とする。

### 9.3 データ品質

```text
PENDING      初回計算中
COMPLETE     対象期間の値が揃っている
INCOMPLETE   欠測日がある
STALE        更新が前々日以前で止まっている
ERROR        取得または計算が失敗した
```

データ品質が`INCOMPLETE`以下の場合でも確認可能な積算値は表示するが、警告枠と欠測日数を併記し、正常値と誤認させない。

### 9.4 参考残り日数

```text
ceil((適期開始温度 - 現在積算温度) / 直近7日の日平均気温平均)
```

有効日が5日未満、平均気温が0以下、欠測が継続中の場合は表示しない。「予報」ではなく「直近の気温傾向による参考値」と表記する。

## 10. API計画

### 10.1 読み取り

```http
GET /api/v1/fields/map?year=2026&bbox=minLng,minLat,maxLng,maxLat
GET /api/v1/fields/{fieldId}
GET /api/v1/fields/{fieldId}/seasons
GET /api/v1/varieties?query=こし
GET /api/v1/variety-rules/resolve?varietyId=...&lat=...&lon=...
GET /api/v1/weather-locations/nearest?lat=...&lon=...
GET /api/v1/parcel-tiles/{z}/{x}/{y}.mvt
GET /api/v1/parcels/hit-test?lat=...&lon=...
```

### 10.2 更新

```http
POST  /api/v1/fields
PATCH /api/v1/fields/{fieldId}
POST  /api/v1/fields/{fieldId}/seasons
PATCH /api/v1/seasons/{seasonId}
POST  /api/v1/seasons/{seasonId}/harvest
POST  /api/v1/seasons/{seasonId}/recalculate
```

田んぼ登録APIは`Idempotency-Key`を受け取り、二重タップによる重複登録を防ぐ。APIはクライアントから渡された`account_id`を信用せず、認証情報から所有者を決定する。

地図APIはGeoJSONで開始し、圃場数や応答サイズが閾値を超えた場合にユーザー圃場もMVTへ移行する。

## 11. 筆ポリゴン取込

全国一括ではなく、最初の実証地域となる都道府県から取り込む。

```text
農林水産省FlatGeobuf
  ↓ ダウンロード・ハッシュ記録
  ↓ 座標系・属性検証
  ↓ PostgreSQL/PostGISへ投入
  ↓ geometry修復・空間インデックス作成
  ↓ MVT配信
```

取込時に以下を記録する。

- 公開年度
- 取得元URL
- 取得日時
- ファイル名とSHA-256
- 対象都道府県・分割番号
- 読込件数、無効形状件数、修復件数

更新時に`maff_parcels`を置換しても、登録済みの`fields.geom`は変更しない。

## 12. PWA・アクセシビリティ

- インストール可能なmanifestとアイコンを用意する。
- アプリシェル、品種マスター、最後に成功したホーム地図応答をキャッシュする。
- MVPのオフライン利用は閲覧のみとし、登録・編集はオンライン時に行う。
- タップ領域は44px以上を目安にする。
- 色だけに依存せず、文字、アイコン、輪郭でも状態を区別する。
- 日差しの強い屋外を想定し、低コントラスト色を避ける。
- 文字拡大時にも主要操作が欠けないようにする。
- 位置情報を拒否されても、地図検索・手動移動で利用できるようにする。

## 13. セキュリティ・プライバシー

- 全通信をHTTPS化する。
- 認証済みユーザーは自分の圃場だけ参照・更新できるよう、APIとDBの両方で制約する。
- セッションCookieは`HttpOnly`、`Secure`、適切な`SameSite`属性を使う。
- `.env`や認証鍵をGitへ保存しない。
- ログにはアクセストークン、位置情報の完全なリクエスト本文、個人情報を出さない。
- 圃場位置は個人の営農情報として扱い、公開共有機能はMVPに含めない。
- DBバックアップと復元手順を本番開始前に試験する。
- 依存関係、コンテナ、シークレットをCIで検査する。

## 15. CI/CD・環境

### 15.1 環境

```text
local       開発者環境
preview     Pull Requestごとの確認環境
staging     本番相当データ構成での受入環境
production  実運用
```

本番の気象取得はstagingと分離し、テストによる外部データ源への重複アクセスを避ける。自動テストでは原則として保存済みfixtureを使う。

### 15.2 CI

Pull Requestごとに以下を実行する。

1. フォーマット・lint
2. TypeScript型チェック
3. 単体テスト
4. PostgreSQL/PostGISを使う統合テスト
5. アプリビルド
6. DBマイグレーション整合性確認
7. 依存関係とシークレットの検査
8. 主要画面のE2Eテスト

`main`へのマージ後にstagingへ自動反映し、productionは手動承認付きとする。

## 16. Git運用

### 16.1 ブランチ

- `main`: 常にレビュー・テスト済みの状態
- 作業ブランチ: `feat/<issue>-short-name`、`fix/<issue>-short-name`、`docs/<issue>-short-name`
- 原則としてPull Request経由で`main`へ取り込む
- マージ方式はSquash mergeを基本とする
- `main`へのforce pushは禁止する

### 16.2 コミット

Conventional Commitsの短い形式を使用する。

```text
feat: add field registration flow
fix: preserve missing weather day warning
docs: define MVP implementation plan
chore: configure CI
```

生成物、大容量の筆ポリゴン原本、秘密情報はコミットしない。DBスキーマ変更には必ずマイグレーション、テスト、必要なロールバック説明を含める。

### 16.3 Pull Request

Pull Requestには以下を記載する。

- 目的と関連Issue
- 変更内容
- 確認方法
- UI変更時のスマートフォン画像
- DB変更と移行上の注意
- 未完了の実機・外部データ確認
